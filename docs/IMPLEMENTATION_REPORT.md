# 阶段 0/1 实施报告

## 完成范围

已建立独立项目、Git 仓库、Python 3.12 虚拟环境、SQLite V1、18 张表、顺序迁移、Repository/Service 分层、金额解析、实体别名结构、事件—文档/投资方、字段证据、去重候选/决定/撤销链、审计日志、质量门槛、不可变 release、五个内部审核页面和自动测试。未实现动态主题、向量、聚类、OpenAlex、公开首页或热点榜。

## 样本状态

真实候选事件：0；去重后唯一事件：0；真实文档：0。来源白名单：8 类，等级分布 S=1、A=2、B=3、C=1、D=1。金额分布均为 0。

原因：低频公开检索的结果质量不足，外部索引接口随后限流。在无法逐条核验原始 URL、主体、融资事实和字段证据的情况下，项目选择不为凑满约 30 条而导入搜索摘要或编造事件。自动测试使用固定、脱敏、`.invalid` 域名 fixtures，fixtures 不写入开发账本，也不代表真实市场。

这意味着工程闭环已验证，但“约 30 个真实候选事件的小样本验证”尚未完成，是进入下一阶段前的明确阻塞项。建议由用户提供一批起始 URL，或下一轮为白名单来源安排受控、可人工复核的采集时段。

## 测试

29 项 pytest/AppTest 全部通过。覆盖空库迁移、幂等、外键与约束、精确/模糊/累计/未披露金额、CNY/USD/EUR、企业英文别名、同名不同主体、多文档唯一事件、补充披露、不同轮次冲突、去重撤销、字段证据、发布阻断、仅 D 级阻断、release 不可变/可复现、原科研路径拒绝、只读 Repository、敏感信息扫描和全部内部页面渲染。

## 已知问题

1. 未完成真实约 30 候选事件录入，因此 UI 当前为空账本。
2. 实体页面已展示主体/别名和风险说明，V1 尚未加入完整的表单式新建/合并动作；数据库与审计结构已支持。
3. 事件页面以字段/证据核查为主，完整状态变更表单仍需在真实样本到位后按工作流细化。
4. 去重 V1 尚未计算投资方和引用链的实际分数，字段已预留，当前为 0。
5. `releases.status` 设计含 withdrawn，但不可变触发器阻止原地撤回；正确做法应在下一迁移增加独立 `release_status_history`，不要修改旧 release。
6. V1 为本地单用户；未来需要身份系统时必须保留 actor，不应以共享账号覆盖。

## 下一阶段建议（不在本轮实施）

先补齐并双审 20–30 个真实候选事件，形成去重与字段证据黄金集；达到发布门槛后再开始“动态术语提取与候选主题发现”。阶段 2 只应增加 span-grounded 的产品/技术/应用/用途词、原始词与标准词、版本化向量和候选主题，不直接自动发布主题，也不引入 OpenAlex 作为发现边界。
